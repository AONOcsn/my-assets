# 净值 · 本地资产

一个离线优先、只把数据保存在设备浏览器中的个人资产管理网页。首次在线打开后，网页资源会被缓存；此后无网络也能查看数据和记账。只有在设置页主动更新汇率时才访问网络。

## 资产盘点

- **总览**：查看净资产、历史变化与按账户类型／币种展示的资产分布；右上角可隐藏金额。
- **账户**：直接填写当前余额，系统计算差额并保留原流水；批量盘点时，留空表示跳过，填 `0` 表示余额归零。同余额也可保存本次核对时间。
- **账户详情**：盘点历史、账户信息和关联流水分开呈现。排序、归档和恢复在管理模式中；有流水或盘点历史的账户不能直接删除。
- **设置**：主币种、汇率、备份恢复；分类管理在辅助功能中。流水记账通过账户页的「资金流水」进入。

净资产变化包含资金进出、账户归档和汇率变化，不是投资收益率。历史估值采用记录时的余额与汇率；缺少当时汇率的位置留空。旧版升级只建立当前基线，不推算过去的资产曲线。

账户币种与主币种均可从主流法币及 USDT、USDC、BTC、ETH 中选择。汇率只能通过设置页的「更新汇率」按钮自动取得；所有账户会按所选主币种统一换算。

## 本地运行

```powershell
npm install
npm run dev
```

生产构建、账本与汇率单元测试：

```powershell
npm run build
npm test
```

生产构建的本地体验：`npm run preview -- --host 127.0.0.1 --port 4173`，然后打开 `http://127.0.0.1:4173/`。本地账本与手机线上账本按来源隔离，不会自动同步。

## 部署到 GitHub Pages

推送到 `main` 分支后，`.github/workflows/deploy.yml` 会自动安装依赖、跑账本单元测试、构建并发布静态站点，无需本地打包。

仓库设置里把 **Settings → Pages → Source** 选为 **GitHub Actions** 即可（首次推送后配置一次）。

上线地址为 `https://<你的用户名>.github.io/my-assets/`。

### 在 iPhone 上使用

1. 用 **Safari** 打开上面的地址。
2. 点底部「分享」按钮 → **添加到主屏幕**。
3. 之后像普通 App 一样从桌面图标启动，全屏无浏览器地址栏，首次在线打开后即可离线使用（不需要从 App Store 安装）。

注意：账本数据保存在该设备的浏览器存储中，不随 GitHub 仓库同步。更换设备前请在设置页导出 JSON 备份。

## 隐私与备份

- 业务数据存于浏览器 IndexedDB，不使用账号或服务器。
- 导出 JSON 是换机或清除浏览器数据前的完整备份方式；导入会覆盖本机现有数据。
- 新备份格式为 `version: 2`，包含盘点时间、历史估值与显示偏好；可以导入旧版 `version: 1` 备份，旧版程序不能读取新版备份。
- 导入前会检查数据并显示账户、流水和估值记录数，可先导出当前账本，再确认替换。保存失败不会关闭表单或提示保存成功；读取失败会提供重试与备份恢复入口。
- 汇率由用户主动更新，调用公开汇率及行情接口，不会上传账本数据。部分失败币种保留原值和真实更新时间。

## 汇率数据源与网络兼容性

汇率由设置页的「更新汇率」按钮主动获取，法币与加密货币分属两个独立数据源，**任一源失败不影响另一类**，已取到的币种仍会写入，失败的币种保留上一次的值。

| 类别 | 主数据源 | 备用数据源 |
| --- | --- | --- |
| 法币 | `open.er-api.com` | `api.frankfurter.app` |
| 加密货币 | `data-api.binance.vision` | `api.coingecko.com` |

每个数据源在超时或报错时会自动切换到下一个上游，单次请求超时 8 秒并带退避重试。

需要这些回退机制，是因为部分上游域名在特定网络环境（例如中国大陆）会连接超时或被重置。实测结果：

- ❌ `api.coingecko.com`、`api.coinbase.com`、`api.binance.com`、`api.kraken.com` —— 超时或被重置，不可达
- ✅ `data-api.binance.vision`、`open.er-api.com`、`api.frankfurter.app` —— 可达且返回 `Access-Control-Allow-Origin: *`

**注意：可用性无法靠域名推断**（`api.binance.com` 不可达但同属币安的 `data-api.binance.vision` 可达），因此代码采用「多源顺序回退」而非依赖单一上游。

### Service Worker 缓存约定

`public/sw.js` 对请求分三类处理，改动时需保持：

- **跨域请求**：直接放行给网络，**绝不缓存**。缓存汇率接口会导致「更新汇率」读到旧响应，表现为一直失败。
- **同源页面导航**：network-first，保证能拿到新版本；断网时回退缓存。
- **同源静态资源**：cache-first（构建产物文件名固定）。

修改应用资源后必须同步提升 `sw.js` 里的 `CACHE` 版本号，否则已安装到主屏幕的设备会继续使用旧缓存。新版资源准备好后会显示「立即更新／稍后」；只有用户接受更新才激活并刷新。表单打开或数据写入期间不可点击更新，避免输入途中突然刷新。设置页提供手动检查入口。

首次从没有更新提示的旧版升级时，旧页面无法显示新界面的提示。请先导出备份，再关闭该站点所有浏览器页面及主屏幕应用，重新打开以让等待中的版本接管。后续版本可使用应用内更新提示。

### 更新已安装到主屏幕的设备（实战经验）

iOS Safari 对已「添加到主屏幕」的 PWA 更新检查较为保守，**旧 Service Worker 会继续用 cache-first 提供旧的 `app.js`**，导致设备上长时间停留在旧版本——表现为修复已经上线，但手机上仍是旧行为、旧文案。

判断依据比"看界面变没变"可靠：设置页底部有 **构建版本** 时间戳。版本号没变就说明仍是缓存的旧版。

强制更新顺序（由轻到重）：

1. 完全退出 PWA（多任务界面上划关闭）后重开，等约 2 秒让其自行刷新。
2. 直接用 **Safari 浏览器**（不是主屏幕图标）打开站点地址，停留片刻。这一步最关键：绕开 PWA 独立进程更容易触发 SW 更新与 `controllerchange` 自动刷新。
3. 若仍旧版，**删除主屏幕图标 → Safari 清空该站点数据 → 重新打开并重新添加**。
   注意：清空网站数据会**连 IndexedDB 里的账本一起删除**，操作前务必先用设置页的「导出 JSON 备份」导出，之后再导入恢复。

> 之所以值得记录：曾出现过修复已部署、CI 全绿、线上产物确认无误，但手机端仍运行旧代码的情况，全部由上述 PWA 缓存行为引起。
